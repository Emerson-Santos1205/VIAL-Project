# VIAL Code of Conduct

**Version:** 1.0.0
**Status:** Draft
**Scope:** VIAL Project, Repository and Community

---

# 1. Purpose

The VIAL project is intended to become a long-lived foundation for organizational cognition.

Its technical objectives require collaboration based on:

* intellectual honesty;
* technical rigor;
* respect;
* transparency;
* reproducibility;
* evidence;
* constructive disagreement.

This Code of Conduct establishes the behavioral principles expected from everyone participating in VIAL.

---

# 2. Scope

This Code applies to participation in:

* source repositories;
* issues;
* pull requests;
* design discussions;
* architecture reviews;
* documentation;
* research;
* benchmarks;
* meetings;
* community channels;
* project events;
* other official VIAL activities.

It applies regardless of role, seniority, employer, nationality, technical background or affiliation.

---

# 3. Core Principle

The VIAL project places the integrity of the project above individual status.

No contributor is more important than:

```text
The Specification
The Evidence
The Organization
The Community
The Long-Term Integrity of VIAL
```

---

# 4. Intellectual Honesty

Contributors MUST represent technical information accurately.

Contributors SHOULD:

* distinguish facts from assumptions;
* identify uncertainty;
* acknowledge limitations;
* cite relevant evidence;
* correct mistakes when discovered.

Contributors MUST NOT intentionally:

* fabricate benchmark results;
* falsify experiments;
* misrepresent implementations;
* conceal relevant failures;
* claim capabilities that have not been demonstrated.

---

# 5. Evidence Over Authority

Technical arguments should be evaluated according to their merit and evidence.

Statements such as:

```text
"I am an expert."
"This company does it this way."
"This is industry standard."
```

do not constitute sufficient technical justification by themselves.

VIAL encourages:

```text
Hypothesis
    ↓
Evidence
    ↓
Experiment
    ↓
Measurement
    ↓
Conclusion
```

---

# 6. Constructive Disagreement

Disagreement is expected.

VIAL explicitly permits strong technical disagreement.

Contributors SHOULD challenge:

* assumptions;
* architectural decisions;
* benchmarks;
* specifications;
* performance claims;
* security models;
* economic assumptions.

However, criticism MUST focus on the idea, implementation or evidence rather than the person.

---

# 7. No Personal Attacks

The following behaviors are unacceptable:

* insults;
* harassment;
* intimidation;
* humiliation;
* threats;
* personal attacks;
* deliberate provocation;
* discriminatory comments.

Technical disagreement is permitted.

Personal hostility is not.

---

# 8. Respect for Contributors

Contributors should assume good faith unless evidence demonstrates otherwise.

Participants SHOULD:

* listen before responding;
* ask for clarification;
* explain disagreements;
* recognize useful contributions;
* avoid unnecessary hostility.

---

# 9. No Appeal to Authority

Leadership does not automatically make an argument correct.

A project leader, maintainer or senior contributor may make decisions, but technical reasoning should remain open to scrutiny.

```text
Authority
   ≠
Technical Truth
```

---

# 10. Protection of the Project's Independence

VIAL should remain technically independent.

Contributors MUST NOT intentionally manipulate specifications or governance solely to create:

* vendor lock-in;
* commercial dependency;
* artificial incompatibility;
* preferential treatment for a specific provider.

Commercial contributions are permitted.

Commercial capture of the architecture is not.

---

# 11. No Vendor Worship

VIAL is provider-independent.

Contributors may advocate for:

* specific models;
* vendors;
* infrastructure;
* implementations;

when supported by evidence.

However, architectural decisions SHOULD remain based on requirements and evidence rather than brand preference.

---

# 12. Experimental Integrity

Experiments MUST be reproducible to the extent reasonably possible.

Benchmark reports SHOULD document:

* workload;
* environment;
* configuration;
* relevant model information;
* evaluation methodology;
* limitations;
* results.

Negative results are valid results.

---

# 13. Benchmark Integrity

Contributors MUST NOT intentionally manipulate benchmarks to create misleading conclusions.

Examples include:

* cherry-picking favorable results;
* hiding relevant failures;
* changing evaluation criteria after seeing results without disclosure;
* comparing incompatible workloads;
* omitting meaningful baselines.

When benchmark methodology changes, the change SHOULD be documented.

---

# 14. Security Responsibility

Security concerns SHOULD be reported responsibly.

Contributors MUST NOT intentionally introduce vulnerabilities.

Security discussions SHOULD prioritize:

* responsible disclosure;
* reproducibility;
* mitigation;
* user protection.

---

# 15. Privacy

Contributors MUST respect confidential and personal information.

The project should avoid unnecessary exposure of:

* credentials;
* private data;
* personal information;
* confidential organizational information;
* proprietary information.

---

# 16. Intellectual Property

Contributors are responsible for ensuring that contributions can legally be submitted to the project.

Contributors MUST NOT knowingly submit material that:

* violates copyright;
* contains stolen proprietary information;
* exposes confidential material;
* improperly incorporates restricted code or documentation.

---

# 17. Attribution

Contributors SHOULD receive appropriate recognition for substantial contributions.

This includes contributions involving:

* architecture;
* implementation;
* research;
* documentation;
* benchmarking;
* testing;
* security;
* project organization.

Recognition should reflect actual contribution rather than hierarchy.

---

# 18. No Credit Manipulation

Contributors MUST NOT:

* claim another person's work as their own;
* deliberately exclude contributors from recognition;
* falsify authorship;
* manipulate contribution history.

---

# 19. Transparency in AI-Assisted Contributions

Because VIAL itself concerns intelligent systems, contributors may use AI-assisted development tools where permitted.

However, contributors remain responsible for submitted work.

AI-generated material MUST NOT be treated as authoritative merely because an AI produced it.

The contributor is responsible for:

* correctness;
* licensing;
* security;
* originality;
* technical validity.

---

# 20. AI Is a Tool, Not an Authority

Within VIAL development:

```text
AI Output
    ↓
Candidate Information
```

not:

```text
AI Output
    ↓
Automatic Truth
```

AI-generated proposals SHOULD be reviewed using the same standards applied to human proposals.

---

# 21. No Fabricated Intelligence

Contributors MUST NOT present simulated or generated organizational behavior as real experimental evidence.

If an experiment uses:

* simulated agents;
* synthetic data;
* generated workloads;
* hypothetical organizations;

this SHOULD be clearly identified.

---

# 22. Documentation Integrity

Documentation is part of the VIAL architecture.

Contributors SHOULD avoid:

* ambiguous terminology;
* undocumented breaking changes;
* unsupported claims;
* misleading examples;
* unexplained deviations from specifications.

When a specification changes, related documentation SHOULD be reviewed.

---

# 23. Terminology Discipline

VIAL depends on precise distinctions.

Contributors SHOULD preserve established distinctions such as:

```text
Organization
≠
Execution Resource

State
≠
Context

Capability
≠
Authority

Model Output
≠
Decision

Information
≠
Evidence
```

Introducing terminology that creates ambiguity should be avoided.

---

# 24. Simplicity

Contributors SHOULD prefer the simplest solution that satisfies the requirements.

Complexity should have a reason.

A proposal introducing a new mechanism should explain:

* what problem it solves;
* why existing mechanisms are insufficient;
* what complexity it introduces;
* what measurable benefit it provides.

---

# 25. Performance Claims

Performance claims SHOULD be supported by measurements.

Statements such as:

```text
"10x faster"
"90% fewer tokens"
"more scalable"
"cheaper"
```

should identify the conditions under which the claim applies.

No performance claim should be presented as universal without sufficient evidence.

---

# 26. Economic Claims

VIAL treats economics as an architectural concern.

Cost claims SHOULD consider relevant components, including where applicable:

```text
Inference
Tokens
Communication
Storage
Synchronization
Validation
Infrastructure
Operations
Human Intervention
```

Optimizing one cost component while significantly increasing total cost should be identified.

---

# 27. Long-Term Thinking

VIAL is intended to be a long-lived project.

Contributors SHOULD consider:

* maintainability;
* compatibility;
* migration;
* operational complexity;
* ecosystem effects;
* future implementations.

Short-term convenience should not automatically override long-term architectural integrity.

---

# 28. Backward Compatibility

Breaking changes may be necessary.

However, contributors introducing breaking changes SHOULD document:

* why the change is necessary;
* what is affected;
* migration requirements;
* compatibility implications.

Breaking changes should be deliberate rather than accidental.

---

# 29. Architectural Neutrality

VIAL specifications should remain independent of implementation details unless those details are intentionally normative.

Contributors SHOULD distinguish:

```text
Normative Requirement
```

from:

```text
Implementation Recommendation
```

and:

```text
Experimental Idea
```

---

# 30. Debate Is Part of the Project

Architectural debate is not a failure of the project.

It is part of the engineering process.

The project encourages questions such as:

```text
Why?

What evidence supports this?

What could falsify it?

What is the cost?

What happens at scale?

What happens when it fails?

What happens when the assumption is wrong?
```

---

# 31. No Artificial Consensus

Consensus should not be manufactured.

A contributor may disagree with a decision after reasonable discussion.

The project should distinguish:

```text
Agreement
```

from:

```text
Decision
```

A decision can be accepted operationally even when not every participant agrees with it.

---

# 32. Decision Documentation

Important architectural decisions SHOULD be documented through the appropriate project mechanisms, including ADRs where applicable.

The purpose is to preserve:

* context;
* alternatives;
* reasoning;
* consequences;
* decision status.

This prevents the project from repeatedly solving the same architectural question.

---

# 33. Conflict of Interest

Contributors SHOULD disclose significant conflicts of interest when they could materially influence a technical recommendation.

Examples may include:

* direct financial interest;
* vendor affiliation;
* ownership of competing technology;
* contractual incentives.

Disclosure does not automatically disqualify participation.

Transparency is the requirement.

---

# 34. Responsible Leadership

Maintainers and project leaders have additional responsibilities.

They SHOULD:

* enforce project standards consistently;
* protect contributors from harassment;
* document important decisions;
* avoid favoritism;
* encourage technical criticism;
* protect the project's long-term interests.

Leadership should serve the project rather than personal status.

---

# 35. Maintainer Authority

Maintainers may make decisions necessary to keep the project functioning.

However, maintainer authority SHOULD be exercised:

* transparently;
* consistently;
* proportionally;
* with documented reasoning for significant decisions.

---

# 36. Enforcement

Violations may result in appropriate actions, including:

1. informal clarification;
2. warning;
3. request to modify behavior;
4. moderation;
5. temporary restriction;
6. removal from project spaces;
7. other appropriate measures.

The response should be proportional to the violation.

---

# 37. Severe Violations

Severe violations may require immediate action.

Examples include:

* credible threats;
* deliberate harassment;
* malicious security attacks;
* deliberate fraud;
* intentional benchmark falsification;
* repeated serious violations.

---

# 38. Good-Faith Errors

Not every mistake is misconduct.

VIAL distinguishes:

```text
Honest Mistake
       ≠
Intentional Deception
```

Good-faith technical errors should normally be handled through correction and learning.

---

# 39. Correction Culture

VIAL should encourage contributors to say:

```text
"I was wrong."
```

without fear of unnecessary humiliation.

Correcting an error improves the project.

Hiding an error damages it.

---

# 40. The Standard of Conduct

The desired standard can be summarized as:

```text
Be rigorous.
Be honest.
Be respectful.
Be evidence-driven.
Be transparent.
Be responsible.
Think long-term.
```

---

# 41. Fundamental Rule

When uncertain about how to behave, contributors should ask:

> **Does this action improve the long-term integrity of VIAL while respecting the people participating in it?**

If the answer is no, reconsider the action.

---

# 42. Final Principle

The VIAL Code of Conduct exists to protect something larger than individual contributions:

```text
Trust
    ↓
Technical Integrity
    ↓
Organizational Integrity
    ↓
Long-Term VIAL Integrity
```

The project can evolve technologically.

It can change its implementation.

It can replace its models.

It can change its contributors.

But it must preserve its commitment to intellectual honesty, technical rigor, respect and evidence.

> **Build boldly. Debate rigorously. Measure honestly. Respect people. Protect the integrity of the Organization.**

# End of VIAL Code of Conduct
